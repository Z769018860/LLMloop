# 翻译差分测试（v1.03）

差分测试要回答的问题是：**我们用来自证的语义模型，和真实 C 编译器在同一段代码上的行为一致吗？**
不一致又分两个方向——模型太宽（把 C 的未定义行为当成有定义，会导出声称成立其实不成立的结论）和
模型太窄（把合法的 C 判成未定义，白丢覆盖）。两个方向都必须查。

数据由 `scripts/translation_diff_v103.py` 生成并执行，产出在
[`experiments/v103/translation_diff/`](../experiments/v103/translation_diff/)
（`summary.md`、`integers_seed1.json`、`loops_seed2.json`、`probe.json`）。
生成器由种子决定，因此结果可从脚本本身复现。

## A. 整数语义：`IntegerABI` vs 原生 C

`llmloop/c_integers.py` 手写了 C 整数算术：整型提升、通常算术转换、字面量类型、强制转换、回绕，
以及它认定的"未定义集合"（有符号溢出、除零、非法移位、负数左移、`INT_MIN / -1`）。
这是全部位精确结论的地基，必须逐条对照真实编译器。

**方法。** 随机生成类型化表达式树（深度 ≤3，10 种整型，18 个二元算子 + 3 个一元算子 + 三目 + 强制转换），
每个用例生成一个 C 函数，用 `gcc -O0 -fsanitize=undefined -fno-sanitize-recover` 编译，按用例单独起进程运行，
比较"值"和"是否有定义"。判定：

| 模型 | 原生 | 判定 |
| --- | --- | --- |
| 有定义 | 有定义且值相同 | `agree` |
| 未定义 | UBSan 报错 | `agree` |
| 有定义 | UBSan 报错 | `model too permissive`（危险方向） |
| 未定义 | 正常结束 | `model too strict` |

**一个工程细节值得写出来。** 最初所有叶子都是常量字面量，于是编译器在**编译期**就把整棵表达式折叠掉，
sanitizer 检查根本没有被发射——所有用例都会"静默一致"。现在的实现把每个叶子都变成函数参数
（`case_k(unsigned short v0, ...)`），操作数一律是运行期的，折叠便不可能发生。

**结果（1200 例，种子 1，gcc 13.3.0）。** `agree` **1199**，`model too permissive` **0**，
`model too strict` **1**。危险方向零例：没有任何一处模型认为有定义、而编译器报未定义。

那一例是 `-(unsigned short)(0x7fffffff + (unsigned short)-2)`。中间加法 `int + int` 溢出，
标准规定是未定义行为，模型判未定义是对的。但编译器在四种操作数来源下都**不报错**、给出回绕值 `-65533`
（`probe.json` 记录了四种形态：函数参数、`volatile` 局部量、常量初始化的局部量、经 `argv` 传入）。
结论是：**这是 UBSan 覆盖不完备，不是模型错**。也正因为原生差分只能证伪不能证全，
本文的位精确证据落在 CBMC 复核（§4c）而不是原生运行上。

## B. 循环翻译：`translate_c` + 重放 vs 原生 C

`llmloop/c_frontend.py` 把"整型参数 + 若干带初值的整型局部量 + 一个 `while` + 尾 `return`"翻译成周期 IR。
差分做法：生成该片段内的程序，编译并用另一份驱动程序调用，把返回值和工具自己的具体重放
（`exact_trip_count` 求迭代次数 + `after_steps` 走这么多步）比较。

**生成器被限制在片段真正接受的形状**：`%` 等算子不在 `_expr` 的支持范围，周期映射必须是线性且幂等的，
所以更新只能是"状态量 + 常量 / 参数 / 参数倍数"。两相（`if (ph == 0) ... else ...`）形态**没有**纳入生成：
`translate_c` 虽然能拆出两相，但 `LoopAnalyzer` 对合成后的周期映射报
`Full-cycle affine map is not unipotent`——这一条属于该前端的已知边界，写在这里以免读者误以为已覆盖。

**结果（80 个程序 × 16 个输入，种子 2）。**

| 结论 | 次数 |
| --- | --- |
| `agree`（域内，值与原生返回值完全相同） | **1095** |
| `outside no-overflow domain`（原生被 UBSan 拦下） | 185 |
| `value mismatch` | **0** |
| 前端不接受的生成形状 | 0（80/80 通过翻译） |

每个程序 16 个输入里，12 个是 0–9 的小值，4 个被**刻意**放到 `int` 边界（`2^31-1`、`-2^31`、`2^31-7`）。
后 4 个里有 185 次原生执行溢出——这些行只记为"越界"，不计为翻译错误：它们正是证书里那条
no-overflow 义务要排除的区域。域内的 1095 次比较，模型与原生**没有一次**不一致。

## C. 这份证据覆盖到哪里、没覆盖到哪里

- **覆盖**：整数语义层（`IntegerABI`，1200 例）与受限 C 前端（`translate_c`，80 程序 × 16 输入）。
- **没覆盖**：165 例对照实际使用的 `scripts/svcomp_translate.py`（把 `main()` 型基准翻译成 `f(params)`）。
  它没有做语义差分，理由与现状要分清：
  1. 它的**接受/拒绝判定**在 165 例上与冻结 CI 运行逐例一致（165/165，见
     [`UNSUPPORTED_AND_JUMPS.md`](UNSUPPORTED_AND_JUMPS.md)），但这是一致性检查，**不是**语义差分；
  2. 它生成的验证条件由 CBMC 在 586 个证书上做过位精确复核（§4c），那只检验**验证条件**，
     不检验"翻译是否保语义"。
  因此"翻译保语义"这条在这条路径上仍属**未直接测量**，论文里不能当作已验证事实。
- **不可外推**：差分只在受支持片段内进行；`goto`、堆、指针、浮点、并发都不在其中。

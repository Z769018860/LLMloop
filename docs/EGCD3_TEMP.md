# `egcd3-both-nt` 的 `KeyError: 'temp'`：三个障碍，不是一个 bug / three obstacles, not one bug

**结论先说。** 缺口清单把它写成"改代码，1 小时，$0"。跑完诊断后这个估算是错的：
这个单元离"可测量"有**三个独立障碍**，其中第三个是语义决策而不是代码缺陷。所以本轮
**不改 `llmloop/`**，只把诊断固化下来——理由见 §4。

诊断脚本：`python scripts/diagnose_egcd3.py`（零调用、约 20 秒）。三行输出如下。

| 阶段 | 做了什么 | 判定 |
| --- | --- | --- |
| A 原样 | 一个字节不改 | `STUCK:Loop bodies must not contain break/continue/return/declarations` |
| B 提升声明（不初始化） | 把循环体里的 5 个 `int` 声明移到函数开头，语义等价 | `STUCK:Initialized named scalar locals required` |
| C 提升并 `= 0` | 同上但带零初始化（**不**语义等价，仅诊断） | `STUCK:top/loop0/body/then/loop1/body/then/loop2/body operations defined` |

程序是扩展欧几里得，外层循环里声明 `int c; int k; int temp;`、内层再声明 `int d; int v;`，
共 5 个。三行判定对应三个不同的检查，任何一个解决都不够。

## 1. 真正的缺陷是"同一份字节给出两种判定"

CI 上这一格是 `ERROR:KeyError:'temp'`，本机是 `STUCK:Loop bodies must not contain ...`。
**同一份源、同一份冻结参数、同一份代码，判定不同**——差别只能来自 pycparser / 解释器版本对
循环体内声明语句的摆放。这比"有一个键找不到"更值得记：

- `ERROR` 在口径上是"工具崩了，不知道它会说什么"；`STUCK` 是"这个程序不在片段里"。两者都是
  "未证出"，但前者让这一格**不是测量**，后者是。
- 于是这一格的标签**取决于跑在谁的机器上**。这正是 §4.11 记的那类缺陷：不是工具的结论，却以
  结论的样子进了产物。

`ERROR` 因此不是"一个键的 bug"，而是**一个不该存在的判定类别**：一个被前端拒绝的程序应当稳定
地报 `UNSUPPORTED`，无论 pycparser 怎么排这棵语法树。

## 2. 为什么 B 和 C 都不能当修法

- **B（提升声明）语义正确**：`int temp;` 在循环体里就是每次进入作用域新建一个未初始化局部；
  把它提出来、不初始化，读它仍然是 UB，工具该报的还报。**但管线接着要求"具名标量局部变量必须
  已初始化"**（`Initialized named scalar locals required`）。这条要求与 C 语义冲突：为了满足它
  就必须给未初始化局部一个值。
- **C（`= 0`）能让管线继续，但它恰好抹掉本工具要检的那件事**：读未初始化变量是 UB，零初始化
  会让一个本来有 UB 的程序变成可证。**用一个不健全的变换换一个判定，是把"未测"换成"测错"。**
- 即使接受 C，还有第三个：内层循环体上的定义性义务（`... operations defined`）仍然失败。

所以这个程序不是"差一行代码"，而是同时落在三个能力边界外：循环体内声明、未初始化局部、
嵌套循环里的定义性义务。

## 3. 这一格该怎么记

- 它**不是测量**，也**不该是 `ERROR`**。正确的标签是 `UNSUPPORTED`（片段之外），与 §4i 对
  `goto`/`switch` 的处理同一口径。
- 计数**不变**：`ERROR`、`STUCK`、`UNSUPPORTED` 在配对里都算"未证出"；对照在同例上是
  `TIMEOUT`，所以这一格本来就落在"都未证出"。§4.10c 的那句"不改变任何配对计数"是对的。
- 下一次该臂重跑时，前端应先在 `_prepare` 里查一遍"循环体内有没有声明"，命中就直接返回
  `UNSUPPORTED`，而不是让下游任一层去崩。**这是 5 行代码，但它会改 `llmloop/*.py` 的字节**，
  见下。

## 4. 为什么这一轮不改 `llmloop/`（而这是一个决定，不是拖延）

`v105`/`v106`/`v107` 三个协议的 `files` 字段逐个哈希了 `llmloop/*.py`、`scripts/spec_v105.py`
与 `resource_capture.py`。动其中任何一个字节，`check_protocols.py` 会把这几份协议报成 `DRIFT`，
需要对每一份追加 `driver_amendments`——而更贵的是另一件事：

**本文的中心主张是"验证器一行未改"（T1/T2、§1b、§5b 第 1 条）。** 为了给一个不影响任何计数的
单元换标签而去改验证器，等于用论文最硬的那句话去换一个更准确的形容词。**这笔交易不划算。**

所以本轮的处理是：把诊断写成可重跑的三行输出（`scripts/diagnose_egcd3.py`），把正确的标签与
它的代价写进这里和 `experiments/v107/e6c/breakdown.md`，**代码保持冻结**。下一次真的需要重跑
这一臂时，`UNSUPPORTED` 应该和声明检查一起进——那时协议本来就要重新冻结。

## 5. 一句话

"补一个 `KeyError`"实际是"支持循环体内声明 + 支持未初始化局部 + 处理嵌套循环的定义性义务"，
三条里任何一条都不是一小时的事，而三条加起来会动到冻结验证器。**一个不影响计数的标签，
不值得动论文的信任基。**

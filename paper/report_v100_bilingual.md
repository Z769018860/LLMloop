# v1.00 报告 / Report (中文 / English) — 多循环证书复核的根因与修复;旧问题的进展

## 中文
**1. 披露的新问题:多循环证书的 CBMC 复核失败(46 个)——根因查明。** 失败**不是**证书的问题,而是 CBMC 自带的循环契约机制(`--apply-loop-contracts` 与 `--dfcc`,两种实现都如此)对嵌套循环的处理与我们验证器实现的证明规则不等价。证据:(i) 手写一个等价的"外层头 ⇒ 内层入口 ⇒ 内层出口 ⇒ 外层重建"验证条件程序,`Nested-2` 的全部不变式通过,而 CBMC 契约机制报告失败;(ii) 改用**不依赖契约机制的复核**(`scripts/cert_recheck_flat_v100.py`:把证明规则显式展开成普通 C + `__CPROVER_assert/assume`,每个循环一个保持性条件、入口函数 M 中循环被"断言不变式;havoc 被赋值变量;假设不变式且条件为假"替换)后,先前 46 个失败**全部消失**;(iii) 灵敏度检查:故意错误的不变式(外层 `i<=5`、平凡 `True`、HHLP 的 `y<=100`)都被报告 FAILED。复核脚手架还修了两个缺陷(丢弃不存在的标志变量原子;公式用 `__int128` 求值会对高次原子溢出——改为按证书自适应位宽的 `signed __CPROVER_bitvector[W]`)。
**结果(586 个证书,4 批):556 VERIFIED、0 FAILED、29 TIMEOUT、1 ERROR**。新集合上:91 个被证明的程序中 **90 个至少有一个被 CBMC 独立复核的证书**(`DivMinus2` 复核超时)。性质:这是**我们对证明规则的再实现**,换了一个位精确引擎;它检验验证器的实现与算术,不检验证明规则本身;含 `break/continue/return/goto` 的循环报告 UNSUPPORTED。
**2. 旧问题的进展。** (a) **证伪器**加了"持久选择"遍(nondet 总取同一值,模拟总走同一分支的长运行,每个见证仍可重放):有溢出程序 +2 个(`NonTerminationSimple5`、`random1d-1`);(b) 用该遍检查仍未判定的无溢出程序又发现 **2 个基准标签错误**:`AliasDarteFeautrierGonnord-SAS2010-Fig1` 与 `ChawdharyCookGulwaniSagivYang-ESOP2008-random1d`(预期 `true`,实有可重放溢出见证;**累计 4 个标签错误**:另有 `easy2`、`Fig9a`;没有任何工具对这 4 个给 TRUE)。更新后的开发集:**63 个无溢出、110 个有溢出**,我们判定 **169**(61 证明 + 108 见证),Ultimate 156;我们独有 16、Ultimate 独有 3;未判定:2 个无溢出(`nestedLoop-1`——Ultimate 证出;`FMCAD2013-Fig1`)和 2 个有溢出(`counterex1b`、`PodelskiRybalchenko-LICS2004-Fig2`)。
**3. 仍未解决。** 修复轮仍是边缘贡献(新集合 350 个证明里 3 个);`ps4–ps6`、`hard`、`divbin` 等 nla 程序(次数 ≥4 的幂和、二进制除法循环)仍未认证;`nestedLoop-1`、`FMCAD2013-Fig1` 仍未证;4 个标签错误提示基准本身有噪声,**开发集上的"预期无溢出"数字应以见证为准**;新集合没有真值标签(用一致性与独立复核替代)。
## English
**1. The disclosed problem — multi-loop certificate re-check failures (46): root cause found.** They are **not** certificate problems: CBMC's own loop-contract machinery (`--apply-loop-contracts` and `--dfcc`, both implementations) treats nested loops differently from the proof rule our verifier implements. Evidence: (i) a hand-written equivalent verification-condition program ("outer head ⇒ inner entry ⇒ inner exit ⇒ outer re-established") passes for all invariants of `Nested-2` while the contract machinery reports failure; (ii) with a **contract-free re-check** (`scripts/cert_recheck_flat_v100.py`: the proof rule expanded into plain C + `__CPROVER_assert/assume`; a preservation condition per loop; in the entry function M every loop is replaced by "assert invariant; havoc assigned variables; assume invariant and condition false") **all 46 earlier failures disappear**; (iii) sensitivity check: deliberately wrong invariants (outer `i<=5`, trivial `True`, HHLP `y<=100`) are reported FAILED. Two harness defects were fixed too (atoms mentioning non-existent flag variables are dropped; `__int128` evaluation overflowed for high-degree atoms — replaced by a width-adaptive `signed __CPROVER_bitvector[W]`).
**Result (586 certificates, 4 batches): 556 VERIFIED, 0 FAILED, 29 TIMEOUT, 1 ERROR.** On the fresh set 90 of the 91 proved programs have at least one independently re-checked certificate (`DivMinus2` times out). Nature: **our own re-implementation of the proof rule** on a bit-precise engine; it tests the verifier's implementation and arithmetic, not the proof rule itself; loops with `break/continue/return/goto` are UNSUPPORTED.
**2. Progress on old problems.** (a) A "persistent choice" falsifier pass (nondet always returns the same value — long runs that always take one branch; every witness still replays): +2 overflowing programs (`NonTerminationSimple5`, `random1d-1`); (b) the same pass over the still-undecided overflow-free programs found **2 more benchmark label errors**: `AliasDarteFeautrierGonnord-SAS2010-Fig1` and `ChawdharyCookGulwaniSagivYang-ESOP2008-random1d` (expected `true`, replayable overflow witnesses; **4 label errors in total** with `easy2` and `Fig9a`; no tool answers TRUE on any of the 4). Development set now: **63 overflow-free, 110 overflowing**; we decide **169** (61 proofs + 108 witnesses) vs Ultimate 156; ours-only 16, Ultimate-only 3; undecided: 2 overflow-free (`nestedLoop-1` — Ultimate proves it; `FMCAD2013-Fig1`) and 2 overflowing (`counterex1b`, `PodelskiRybalchenko-LICS2004-Fig2`).
**3. Still open.** Repair rounds remain marginal (3 of 350 proofs on the fresh set); nla programs (`ps4–ps6`, `hard`, `divbin`) still uncertified; `nestedLoop-1` and `FMCAD2013-Fig1` unproved; 4 label errors show the benchmark is noisy, so "expected overflow-free" numbers on the development set should be read against witnesses; the fresh set has no ground-truth labels (consistency and independent re-check instead).

## 补充(v1.01):nla 幂和程序——瓶颈定性 / addendum: nla power-sum programs — where the bottleneck is
## 中文
**测试了生成器侧与验证器侧哪个是瓶颈。** (a) 新增析取界原子 `v <= a or v <= b`(`v <= max(a,b)`,仅多项式配置):`nestedLoop-1` 与 `FMCAD2013-Fig1` 仍未认证;(b) 带具体反例的 LLM 混合方案(4 个模型、最多 3 轮)在 `ps3`–`ps6`、`hard`、`divbin2`(带断言的版本)上**全部 STUCK**;(c) 对 `ps4` 手工给出几乎完整的不变式(`y == c`、`c >= 0`、`4*x` 等于四次多项式、按 `k` 符号分情形),交给未改动验证器,仍是 **UNKNOWN(卡在返回表达式的出口义务)**。结论:这几个程序的瓶颈**不只是生成器**,也有**验证器的非线性求解能力**(四次多项式加符号分情形);验证器与其求解配置是约定不动的信任基,我不为数字好看去改它。因此 `ps4–ps6`、`hard`、`divbin` 保持"未解决,瓶颈在非线性求解"。
## English
**Which side is the bottleneck — generator or verifier?** (a) A new disjunctive-bound atom `v <= a or v <= b` (`v <= max(a,b)`, polynomial profile only): `nestedLoop-1` and `FMCAD2013-Fig1` stay uncertified; (b) the LLM hybrid with concrete counterexamples (4 models, up to 3 rounds) is **STUCK on all** of `ps3`–`ps6`, `hard`, `divbin2` (assertion-bearing versions); (c) giving `ps4` an almost complete hand-written invariant (`y == c`, `c >= 0`, `4*x` equal to the quartic, case split on the sign of `k`) to the unchanged verifier still returns **UNKNOWN at the exit obligation of the return expression**. So the bottleneck is **not only the generator**: it is also the **verifier's nonlinear solving power** (quartic polynomial plus sign case split); the verifier and its solver settings are the agreed trust base and I will not change them to improve numbers. `ps4–ps6`, `hard`, `divbin` therefore stay "unsolved, bottleneck in nonlinear solving".

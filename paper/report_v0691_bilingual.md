# v0.69.1 报告：I_nested 跟进、真实代码覆盖率与循环索引规范化 / I_nested follow-up, real-code coverage, loop-index normalization

## 1. 反馈修复（Study R-If） / Feedback repair
**中文。** 对 Study If 第 0 轮中“有候选但未认证”的 40 个响应（26 个安全、14 个不安全）做最多 2 轮反馈修复：安全程序修复成功 5/26（I_nested 3/18、I_noelse 1/6、I_guard 1/2），不安全 0/14 被认证。结论：反馈修复对分支内循环增益很小，与循环树语料一致。
**English.** Up to two feedback rounds on 40 rep-0 failures that had candidates (26 safe, 14 unsafe): 5/26 safe repaired (I_nested 3/18), 0/14 unsafe certified. Repair adds little, as on the loop-tree corpus.

## 2. 累积规则提示的留出确认（Study IfR） / Held-out test of the accumulation-rule prompt
**中文。** 新种子语料（19 安全 + 5 不安全；与第一套源码恰有 1 个程序相同），6 模型 × 24 程序 × 2 提示臂 × 2 重复 = 576 次生成，协议先冻结。**结果为否定：** 基础臂 151/228（66.2%），规则臂 148/228（64.9%）；配对 13:16（符号检验 p=0.71）；聚类 bootstrap 差值 −1.3 个百分点（95% CI −5.3 至 +2.2）；I_nested 两臂均为 15/60。不安全对照两臂各 60 次，0 次认证。因此“失败源于漏掉外层累积量、提示规则可补救”的假设**未得到支持**。对 I_nested 失败的抽查显示：失败多出现在外层循环的保持（preserved）义务（35 次）和无候选（29 次），模型常给出基于 `(i+1)//2` 之类 floor 的更紧但不归纳的上界；这是观察，不是已验证的解释。（提示中的规则含与 I_nested 相似的示例，因此本来就偏向规则臂；即便如此无增益。）
**English.** Fresh-seed corpus (19 safe + 5 unsafe; exactly one program has identical source to the first corpus), 6 models × 24 programs × 2 arms × 2 reps = 576 generations, protocol frozen first. **Negative result:** base 151/228 (66.2%) vs rule 148/228 (64.9%); paired 13:16 (sign test p=0.71); cluster-bootstrap difference −1.3 pp (95% CI −5.3 to +2.2); I_nested 15/60 in both arms; 0/120 unsafe certified. The hypothesis that failures come from omitting outer-loop accumulation and that an explicit rule fixes it is **not supported**. Inspecting I_nested failures, most are at the outer loop's preservation obligation (35) or no candidate at all (29); models often propose tighter floor-based bounds (e.g. `(i+1)//2`) that are not inductive — an observation, not a verified explanation. The rule text contained an I_nested-like example, which favoured the rule arm, yet there was no gain.

## 3. SV-COMP 覆盖率（静态，描述性） / Static coverage on SV-COMP
**中文。** 基准：`sosy-lab/sv-benchmarks`（commit 2e1723f）的 loops、loop-lit、loop-invariants、loop-simple、loop-acceleration、loop-new，共 155 个程序、295 个循环（164 个 for、129 个 while、2 个 do-while）。按首个阻塞特征分类：数组/指针 48、while/do-while 65、非规范 for 24、用户函数调用 9、无循环 9、**落入支持片段 0**。其中 for 循环仅 3/164 为规范形，**原因几乎全是“循环索引在 for 外声明”（161/164）**。这只是静态语法分类：SV-COMP 的性质是可达性断言，而本系统证明的是“无未定义行为”，二者不同；片段兼容也不代表可证明。
**English.** 155 programs / 295 loops (164 `for`, 129 `while`, 2 `do-while`) from six SV-COMP loop directories (commit 2e1723f). First-blocker classification: arrays/pointers 48, while/do-while 65, non-canonical for 24, user function calls 9, no loops 9, **in-fragment 0**. Only 3/164 `for` loops were canonical, almost entirely because the index is declared outside the `for` (161/164). This is a static syntactic classification; SV-COMP checks reachability assertions while this system proves absence of undefined behaviour, and fragment-compatibility does not imply provability.

## 4. 修复：循环索引规范化 / Fix: loop-index normalization
**中文。** 新增 `llmloop/loop_index_normalize.py`（属于受信的验证流程）：当标量 `i` 只在以 `i = a` 初始化的 for 循环内使用、只声明一次、且同一变量的循环互不嵌套时，把 C89 风格 `int i; for(i=a;…)` 改写为 `for(int i=a;…)`；同一变量用于多个循环时，第 1 个保留原名，第 k 个改名 `i_k`（候选须使用这些名字）。不满足条件（循环后读取 i、无初始化赋值、第二个循环接续上一个 i、同变量嵌套）时不改写。测试 `tests/test_loop_index_normalize.py`（原生差分、不安全程序不被认证等）通过。**效果：** 规范 for 循环 3→115/164（70%），程序级出现 3 个完全落入片段的程序和 8 个仅因 nondet 输入而被阻塞的程序；仍被 while（65 个程序）、数组/指针（48）等阻塞。这些仍是静态统计，尚未对 SV-COMP 程序做验证或 LLM 实验。
**English.** New `llmloop/loop_index_normalize.py` (part of the trusted pipeline) rewrites C89-style `int i; for(i=a;…)` to `for(int i=a;…)` when `i` is used only inside loops that initialize it by assignment, is declared once, and same-variable loops do not nest; reused indices are renamed `i_k` for k≥2. Unsafe cases are left alone. Tests include a native differential run. **Effect:** canonical `for` loops 3 → 115/164 (70%); at program level 3 programs now fall fully inside the fragment and 8 more are blocked only by nondeterministic inputs; `while` (65 programs) and arrays/pointers (48) still block most. Static statistics only — no verification or LLM run on SV-COMP programs yet.

## 5. 局限与下一步 / Caveats and next steps
**中文。** 以上均为合成语料或静态统计；规则臂否定结果说明失败原因尚不清楚；无加速声明；`claude-dsflash-itkk` 是 DeepSeek V4.1 Flash 别名。下一步：(1) `while` 规范化（`while(i<n){…;i++}` → for，须保证索引在循环后无用）；(2) 把 SV-COMP 的 nondet 输入映射为参数并重写断言为“无 UB”目标，对覆盖到的程序做验证 + LLM 实验；(3) I_nested：研究失败的真正原因（如检查模型候选是否因 floor 表达式而不归纳），而非继续加提示；(4) 外部工具（ESBMC/CPAchecker/Ultimate）与对称 MALICE 对比；(5) 多重复与成本分析；(6) 中英文论文整合。
**English.** All evidence is synthetic or static; the negative IfR result means the I_nested failure mechanism is still not understood; no speedup claims; `claude-dsflash-itkk` is a DeepSeek V4.1 Flash alias. Next: (1) `while` normalization; (2) map SV-COMP nondet inputs to parameters and recast assertions as a no-UB goal, then verify + run LLM studies on covered programs; (3) diagnose I_nested failures directly (e.g. test whether floor-based candidates are non-inductive) rather than adding prompts; (4) ESBMC/CPAchecker/Ultimate and a symmetric MALICE comparison; (5) repetitions and cost analysis; (6) bilingual paper consolidation.
